# STRATA backend

Supabase project backing [strataroast.com](https://strataroast.com).
Frontend lives at [Gipper37/strata-app](https://github.com/Gipper37/strata-app).

## Repo layout

```
supabase/migrations/  — every schema change, ordered by timestamp
supabase/functions/   — edge functions (Stripe webhook, signup, etc.)
supabase/templates/   — Supabase Auth email templates
schema.sql            — derived snapshot of live DB (do NOT edit by hand)
scripts/              — one-off + recurring data tools
onboarding/           — legacy HTML served by *-page edge functions
```

## Migration workflow

**The rule: commit before push. Always.**

```bash
# 1. write the migration
vim supabase/migrations/$(date +%Y%m%d%H%M%S)_my_change.sql

# 2. commit it
git add supabase/migrations/<file>
git commit -m "Add my_change: <what + why>"

# 3. apply to STAGING (default) and verify
./scripts/db-push.sh

# 4. push the commit so CI replays from scratch and confirms
git push
```

When staging looks good, promote to prod with the release helper:
```bash
./scripts/release.sh
```

Which tags the current `main` as `release-YYYY-MM-DD` and pushes the tag.
CI picks up the tag and applies migrations + deploys edge functions to prod.

`scripts/db-push.sh`:
- DEFAULT: targets **staging**. Safe to iterate.
- `--prod` flag targets prod and requires typing the project ref to confirm.
  Reserved for emergencies; the canonical prod path is the release tag above.
- REFUSES to run on a dirty tree (uncommitted changes under `supabase/`
  or `schema.sql`). This stops the drift that produced 349 untracked
  migrations between Feb and May 2026.

Emergency override for dirty tree: `FORCE_DIRTY=1 ./scripts/db-push.sh`,
then commit immediately.

## CI

| Workflow | Trigger | Effect |
|---|---|---|
| `migration-lint.yml` | every PR + push | Validates filename pattern, no duplicate timestamps, no empty migrations |
| `db-push-staging.yml` | push to `main` | Applies migrations + deploys edge functions to STAGING |
| `db-push-prod.yml` | tag `release-*` | Applies migrations + deploys edge functions to PROD |

### Required GitHub secrets

| Secret | Where to get it |
|---|---|
| `SUPABASE_ACCESS_TOKEN` | https://supabase.com/dashboard/account/tokens |
| `SUPABASE_STAGING_REF` | Staging project settings → General |
| `SUPABASE_STAGING_DB_PASSWORD` | Staging project settings → Database |
| `SUPABASE_PROD_REF` | `pwpslalerytymorcodlv` |
| `SUPABASE_PROD_DB_PASSWORD` | Prod project settings → Database |

CI is dormant until staging is created and secrets are added.

## Release process (once CI is live)

1. Develop on `main` (PRs welcome).
2. Merge to `main` → staging gets the changes automatically.
3. Verify in staging.
4. **Pre-release RLS check** (read-only, safe to run against prod):
   ```bash
   ./scripts/rls-cross-tenant-test.sh prod   # no policy errors / leaks
   ./scripts/rls-two-tenant-test.sh prod     # 2 real users, no overlap
   ```
   Both must pass before tagging a release.
5. `git tag release-YYYY-MM-DD && git push --tags` → prod gets the changes.

## Local development

```bash
supabase start                    # spin up local DB on Docker
supabase db reset                 # replay all migrations from scratch
```

If the local DB doesn't come up clean, the migration history is broken.
That's a stop-the-line bug.

## Schema reference

`schema.sql` is regenerated by `supabase db pull --linked`. It reflects
the live prod state, **not** the union of migration files (those may
differ if something was applied out of band — which should now be
impossible thanks to the push guard).
